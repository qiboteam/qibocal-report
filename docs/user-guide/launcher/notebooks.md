# Desktop Launcher: Notebooks & Queues

## 📓 Notebook sessions

**Notebooks** is the graphical face of `qibocal notebook`, laid out as **Servers** is: the page opens on the **Registered sessions**, with their count and **Refresh**, and **New session**, in the top-right corner, opens the form for a new one. **Where it runs** comes first, as for a server: **This machine**, for a direct connection to the instruments; the **Access node** SSH reaches, for offline processing or setups without queues; or a **Computing node** of a SLURM partition, reached from there. Every place keeps the same features — the kernel environment and its requirements, **Regenerate env**, **Reports** — and the form shows only the fields that make sense there: the SSH destination from the access node on, required there, and the partition, srun options, subnet and where to regenerate for a computing node only, the partition required. Every option of the command line is a control:

- **SSH destination** — empty for a local session.
- **SLURM partition**, and **Interface**: JupyterLab or Marimo.

Under **More options**, with their defaults:

- **Extra srun options**.
- **Working directory**, chosen with the file browser for local sessions.
- **Kernel environment** on the computing node, `qibocal` by default, under the same `~/.cache/qibocal/envs/` as the launcher's own environment.
- **Computing node subnet**, validated the way Python's `ip_network` validates it: a network with host bits set is refused before the command is run. Left empty, the computing node binds the notebook to the interface it routes through to reach the access node, leaving out any address the two nodes share — a container bridge every host has at the same address, say — and the access node checks that it can reach the notebook before forwarding to it; when it cannot, the session fails with the address it tried and this is the option to set.
- **Remote execution**: a connection of the **Remote execution** tab, where qibocal-widgets' `Remote` plugin runs the notebook's acquisitions, *None* by default. The session exports its name as `QIBOCAL_WIDGETS_CONNECTION` and writes the connection to `remotes.json` where it runs, so `Remote()` finds it with no change to the notebook; only the connections that make sense from where the session runs are offered.
- **Kernel requirements**, in `requirements.txt` format, one requirement per line: what the kernel environment must hold beyond `qibocal`. They are installed when the environment is created; whenever the list changes, the next session installs it with pip on top of the existing environment, which is never rebuilt — nothing is uninstalled, and the requirements last installed are recorded inside the environment, so an unchanged list costs nothing. A failed installation stops the session, and is tried again at the next one. On the command line, `--requirements` takes the text or `@requirements.txt`.
- **Startup timeout**.

Named connections are read from and written to `notebooks.json`, the file `qibocal notebook add` manages, so a connection saved here is usable as `qibocal notebook connect <name>`. Only the options that differ from the defaults are stored.

**Open and register** keeps the new session in `notebooks.json` under its **Name** and opens it; **Open** opens it for a look, saving nothing.

Every registered session is a card, with the same actions as a server's. **Start** opens a session with its options — while one runs, the card wears a *running* pill leading to Running, and **Open** takes its address to the browser. **Regenerate env** deletes the session's kernel environment entirely, with everything ever installed in it, and creates it again from `qibocal` and the session's **Kernel requirements** alone, all in a single install — after asking, since it cannot be undone, and only while no session of it runs; it is `qibocal notebook rebuild`, and its output is in **Running**. For a SLURM session it runs on the access node, where nothing waits in the queue — the environment lives in a home the nodes share — unless **Regenerate env on** asks for a computing node, under **More options**: then it goes through srun like a session, and its queue shows in **Running** as a session's does. Only a Python virtual environment is ever removed: a folder without `pyvenv.cfg` is refused. **Reports** shows the reports a session's calibrations write: it starts a report server on the same channel — the same SSH destination, with its own connection and the same credentials — serving the session's **Reports folder**, and opens it in the dashboard; while that server runs, the button opens it again. It is started for a look, as *<session> reports*: nothing is written to `servers.json`, and it stays in the dashboard only while it runs. The **Reports folder**, under **More options**, is relative to where the session starts — the working directory, or the home folder — and is created when the session starts; it is exported to the notebook and its kernels as `QIBOCAL_REPORTS_DIR`, for the code there to write its reports to, while the working directory, and the files the notebook sees, stay as they are. Without one, Reports serves where the session starts. The server runs on the access node, never through SLURM, in an environment of its own, `qibocal-report` under `~/.cache/qibocal/envs`, since the kernel environment's `qibocal` command is the calibration library's. A notebook's card in **Running** has the same button. **Edit** opens the form on the session, its name included, **Duplicate** opens the form for a new session with its options, and the bin forgets it — its environment stays.

Opening a session runs it with `--no-interactive`: the address appears in **Running** as soon as the session answers.

Environments are made and filled with [uv](https://docs.astral.sh/uv/), far faster than venv and pip: `uv venv --seed` — pip is still in every environment, for whoever uses it — and `uv pip install`. The uv on the machine's `PATH` is used, or one installed once under `~/.cache/qibocal/tools/uv`; without either, or with `QIBOCAL_NO_UV` set, venv and pip as before. The same goes for the environment of a server started on another machine, and for the launcher's own.

## 🧵 SLURM queues

**Queues**, at the top right of **Running** — where **New server** sits on **Servers**, in the quieter tint of the home page's section icons — leads to the page of the queues, as `g q` does.

A notebook session dispatched to a SLURM partition waits in its queue before it runs, and the one looking at it wants to know why: who is ahead, which nodes are busy, whether the partition is up at all. In **Running**, the card of such a session shows its **queue** under the actions — the partition's nodes by state in one line, the jobs in a table with this session's own job marked and first, and, while it waits, where it stands in line. Filters narrow the table to one's own jobs, to a state, or to a text; **Refresh** asks the controller now; **Full view** opens the queue on the **Queues** page (`g q`), where every queue the launcher knows — of the sessions it runs, and of the saved connections — is one click away, with links back to the sessions on it. From a card, `q` goes there.

The columns of the table are dragged at their edge, reset by a double click, and remembered. The job is marked as this session's as soon as it is submitted: the worker names it `qibocal-nb-…` unless the extra `srun` options name it, and the launcher finds it by that name until the compute node reports its id. The home page lists, under what runs, the queues of the running sessions in a line each — how many nodes are busy and free, how many jobs run and wait, and one's own jobs — from the last answer, asked once on arrival and not again while there.

The controller is asked sparingly, since every `squeue` costs it something: once the moment a session is dispatched — so the answer is there when its card appears — then every 30 seconds while a queue is on screen, and never otherwise. The interval is the `queuePollSeconds` preference in `launcher.json`, editable in **Configuration**, and never goes under 10. Several panels on the same queue share one question. The question itself is `qibocal notebook queue`, which runs `squeue`, `sinfo` and `whoami` in a single round trip over the session's own SSH destination.
